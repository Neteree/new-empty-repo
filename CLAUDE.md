# Project notes

A side business building websites for local New Zealand businesses, with AI agents doing most of the building and changes. No monthly fees: clients pay a one-off price for the build, then per request for changes (fixed price for small changes, quoted for bigger ones). Change work comes from our own builds; we don't go looking for work on other people's sites.

## Decisions

- **Scripts before AI (most important):** if a task is deterministic, automate it with a plain script or workflow, never an agent. AI costs money on every run, so use it only where real judgement is needed, and always try the scripted path first (as the change-request workflow does). When building anything new, say which parts are scripted and which, if any, need AI and why.

- **Data-driven sites:** everything a client might change (wording, prices, hours, photos, menu items, news) lives in data files (`src/data/site.json`, module JSON such as `menu.json`, Markdown posts, `src/assets/photos/`), never mixed into page code, so scripts can make most changes. `.ts` files next to the JSON only hold types.
- **AI where it earns its keep:** the build and routine changes are scripted. AI is for judgement and writing: drafting a client's headline and copy from their onboarding answers (Cameron reviews), working out vague requests, and one-off work like new sections. When a kind of request keeps needing AI, write a script for it.
- **Components, built once:** a site is a set of components (hero, menu, hours, news…), each with its own data file. A new site uses the components that exist; only a missing one gets built (by Cameron or AI), in the same shape so themes, checks and scripted changes still work. A one-off stays with that client; once a kind of request or component comes up a second time, it becomes a reusable module or change script. Avoid building a site from scratch: it loses the automation. Keep automation first for now.
- **One way to build everything (most important after scripts):** every site and game, Cameron's own included, is made from `starter/` and `modules/`: never a standalone file or a one-off repo. New work goes in as a module or a shared part (`starter/src/components/`, `starter/src/lib/`), so the next site or game gets it for free. Lists that two places need (looks, add-ons, change types) are read from one source or generated, never copied by hand; a check fails if they drift. Before building anything, look for a part that already does it; if something is built twice, merge it.
- **Simple from first principles:** work out what a thing really is (data, state, rules, display) and build it from small parts that each do one job, composed together. Remove redundancy wherever two things are really the same; keep them apart where they differ for a real reason, rather than forcing one complicated part. Simpler is the test, not fewer files. This is why sites and games are built together: a part that works for both is probably the right shape. Streamlined code also makes for a better experience for clients and visitors: fewer steps, fewer special cases, the same thing working the same way everywhere.
- **No AI at the front for now:** forms sort requests by type and Cameron approves everything. Add an AI step only if free-text requests become common, and then only to translate them into the scripts' change format for Cameron to approve.
- **Payments:** Stripe (payment links; a paid invoice triggers go-live), with bank transfer as a manual fallback.
- **Stack:** Astro 7 with Svelte 5, static output. Svelte 5 runes syntax only (`$state`, `$derived`, `$props`). Sections and components are Svelte (static HTML with no JavaScript unless given a `client:` directive), so the same components work on a site, in an app or in a 3D scene; `.astro` files are only thin shells (pages, layout, module `Section.astro`) that gather data, prepare photos (`picture()` in `src/lib/images.ts`) and place interactive islands. Logic lives in plain `.ts`, not in components.
- **UI and graphics:** text, forms and anything people read or tap are page elements; 3D and games go on canvas with Threlte (three.js in Svelte), both reading the same data. Astro covers sites and game-like projects alike; no SvelteKit or second framework.
- **Stay on Astro + Svelte;** reconsider only if something keeps getting in the way.
- **Shops:** a few products means the `shop` module (Stripe payment links, no cart). A real catalogue means Shopify behind an Astro front end.
- **Not WordPress,** unless a client already runs on it or needs its plugins.
- **Content:** client details live in `src/data/site.json` (typed by `src/site.config.ts`), module lists in their JSON, and news posts in Markdown content collections.
- **Time zone:** all date logic uses the client's time zone (`Pacific/Auckland`), never UTC.
- **Honesty:** never invent facts about a client (prices, hours, allergens, suppliers). Use `[PLACEHOLDER: ...]` and ask.

## Starter plan

- **Base starter** (`starter/`) for every site (clients, Cameron's own, games): config, layout, light and dark mode, optional logo, hero photo (or theme-coloured art until there is one), gallery, news (journal), enquiry form (Web3Forms; optional "Your business" field and thank-you wording in `enquiry`) with address and hours beside it (both optional), optional public phone (tap to call), map link and Instagram/Facebook links (in the Visit section and footer), a site-wide notice (`notice` in `site.json`: text plus an optional last day, hidden after it in NZ time), local search basics (LocalBusiness JSON-LD, canonical link, `sitemap.xml` and `robots.txt` once `url` is set; demo sites are kept out of search), home page section order (`sections` in `site.json`; module sections first by default, then gallery, news, enquire), an optional main button beside the headline (`heroLink`, e.g. "Play now"), optional icons and link-preview image in `public/` (`npm run share-images` draws them from the name, headline and look), 404 page, checks, and the new-client script. Public `phone`, `address` and `social` in `site.json` are separate from the client's private `contact`.
- **Shared parts** (used by modules, never copied into them): `src/lib/send.ts` sends every form (Web3Forms, or the intake Worker when `intakeUrl` is set, which is only on Cameron's site); `src/components/forms/` has the opening-hours picker, photo picker and price-list fields; `src/lib/catalogue.ts` gives the forms the looks (from `themes.ts`) and add-ons (`src/data/modules.json`, written by new-client and update-site from `modules/`; `"offer": false` in a `module.json` leaves it out); `src/lib/game/` has seeded random numbers and the daily game (NZ date), saving and best scores, sound, a hex board and a bot playtest runner; `src/components/game/GameDialog.svelte` is the pop-up for rules, game over and "start again?". `src/components/SectionHead.svelte` is the top of every section and page (note, heading, intro). `src/lib/money.ts` shows every price the same way (cents only when a list has them) and reads typed prices for the forms and change scripts. Named items (menu, price list, shop) share one way to be found, added and photographed in `scripts/changes.js`. `src/components/forms/PhotoChoice.svelte` picks one photo for an item (new upload or one on the site). **List sections** (reviews, questions, highlights, steps, past work) are described once, in their `module.json` `"list"` (fields, which one identifies an item, wording). From that one description come their change scripts (`<type>-add`, `-remove`, `-replace` in `scripts/lists.js`), their request form fields (`src/components/forms/ListFields.svelte`) and their queue wording, so a new list section needs only its data, its look and that description. Other change types need a handler in `scripts/changes.js`, a form option and a line in `describeChange()` in `ops/lib.js` (`node ops/check.js` and the request module's check fail if one is missing); uploaded photos in any change are matched up by `ops/pull.js` without a list. The new-website form fills list sections (reviews, questions, highlights, steps) from their descriptions, allows no opening hours, and sends an estimate and any extras; `onboard.js` turns it into the client JSON. A module can ship `check.js`, which `npm run check` runs (the change form checks its change types against `scripts/changes.js`; Lantern Market replays recorded games and runs bot playtests).
- **Photos:** onboarding has logo and photo upload buttons (through the intake Worker) and the client picks a main photo (the first by default), and approving an onboarding adds them automatically: the main one beside the headline, the rest in the gallery (descriptions still needed; the checks list them). Photos emailed later go in with `logo` and `gallery-add` changes.
- **Add-on modules** (`modules/<name>/`) per client type: food is done (a plain menu grouped by category; weekend-style pre-ordering is optional, `"menu": { "preOrder": true }` in the client JSON or `&preorder=1` in the onboarding link); prices is done (a price list for anything sold at set prices: one price, "from", sizes or "ask us", optional photos from uploads or the gallery, groups, hide for now, a note under the list; `clients/florist-demo.json`); booking is the "booking or quote form" add-on for services and trades (one module: `"booking": { "kind": "quote", "options": [...] }` in the client JSON, or `?modules=booking&quote=1` in the onboarding link; choices start as a placeholder until the client gives them, then a `booking` change; `clients/trades-demo.json`); bouquet is the first 3D module (a Threlte bunch of flowers people can turn, with a "New bunch" button; the pattern for 3D sections: its own section, loaded as an island only when scrolled to), and it adds a game page, `game.html` ("Make the bunch": tap the flowers each customer orders before time runs out; rules in `game.ts`, 3D garden in `Garden.svelte`, order, timer and score as page elements; a module can add pages from its own `src/pages/`); minigolf is a full 3D game: `play.html` with four holes of mini golf (drag back from the ball to putt, or aim and power sliders with a Putt button), a scorecard and best round, and a home page section listing the holes (`clients/minigolf-demo.json`; physics as plain functions in `golf.ts`, holes in `minigolf.json`); reviews is customer quotes with optional stars and source; faq is questions and answers (open and close, no JavaScript); shop is a few products with Stripe payment links (Buy button per product, "Ask us" without a link, sold out; `clients/shop-demo.json`), not a cart; highlights is a row of short "why us" cards; steps is numbered how-it-works steps; work is past projects with a picture each (a "Demo" tag for anything that isn't real client work; screenshots can sit in a browser frame); lantern is Lantern Market, a full night-market tile game on `lantern.html` with a home page section (rules in `lantern.ts`, wording and content in `lantern.json`; `clients/lantern-demo.json`, a game-first site on the night look); start is Cameron's one public "Get started" form, `start.html` (only on his site, `"offer": false`): a new website (their business; "Build your site", one list of what's included and the add-ons with prices from his price list, plus "Something else?" for anything that doesn't exist yet, quoted; a look; contact details), a change to their website (the change request form) or a question. Nothing is built, changed or shown to the client until Cameron has checked it. The old `onboarding.html` and `request.html` links redirect to it. Prices, FAQ, steps and work can each add a menu link (`section.nav`); menu links follow the home page section order. A module with a data file names it in `module.json` (`"data": "reviews.json"`) and the client JSON key of the same name (`"reviews": { "items": [...] }`) is laid over it, so demos and real clients start without placeholders. A module that needs packages lists them in `module.json` (`dependencies`), and new-client adds them to the site's `package.json` (run `npm install`). A module adds `src/modules/<name>/Section.astro` (a thin shell for its home page section, with the markup in a Svelte component such as `Menu.svelte` or `PriceList.svelte`) and optionally `NavItem.astro` (a menu item); the starter picks them up automatically.
- Update an existing client site to the latest starter and its modules: `node starter/scripts/update-site.js <site-folder>` (`--dry-run` to see what would change). It replaces code only, never the client's content (site.json, photos, posts, module data, lock file), fills in new settings with their defaults, merges package.json and spelling words, and removes files an older starter had (tracked in the site's `.starter-files.json`). `--add <module>` brings in an add-on the site doesn't have yet (e.g. one a client just bought) and `--remove <module>` takes one out. Then `npm install && npm run check` in the site, and push it.
- Create a client site: `cd starter && node scripts/onboard.js <onboarding-email> <folder>` from onboarding answers, or `node scripts/new-client.js clients/<client>.json <folder>` from a client JSON. The client JSON lists its `modules`. See `clients/example.json` (no modules), `clients/bakery.json` (food), `clients/florist-demo.json` (prices and bouquet), `clients/trades-demo.json` (quote form), `clients/minigolf-demo.json` (mini golf game), `clients/services-demo.json` (barber: bookings, prices, reviews, questions, notice) and `clients/shop-demo.json` (gift shop: shop, reviews, questions, own section order) and `clients/lantern-demo.json` (a game site: Lantern Market on the night look). All demos are built and checked in CI. `clients/cameron-belcher.json` is Cameron's own site (its photos live in his repo, so CI doesn't build it here).
- **Looks:** presets in `starter/src/themes.ts`, picked with `theme` in the client JSON: bold, classic, calm, warm, night (dark in both modes, made for Lantern Market) and studio (Cameron's own, `private`, not offered to clients). Colours are CSS variables (`--accent`, `--highlight`, `--paper`, `--ink`…); modules must use them, never hard-coded colours (a game's own piece colours are data in its JSON). The onboarding and change forms show the looks straight from `themes.ts`.
- **Checks:** GitHub Actions run them on every pull request (`.github/workflows/check.yml` in each site; `starter.yml` here tests the starter). `npm run check` in any site builds it, then checks HTML, NZ/UK spelling (`cspell-words.txt`), phone and desktop layout, images, links, empty-form errors, leftover `[PLACEHOLDER: ...]` text, and accessibility including colour contrast in light and dark mode (axe-core). Screenshots go in `check-output/`. Each module's own `check.js` runs too. Cameron's site gets the checks like any other site, through update-site.

## Agents

- `site_agent.py`: a Strands agent on Gemini Flash that applies a client change request to a site. Its tools can only touch the site's `src/`, and it must pass the build. It falls back 3.8 → 3.7 → 3.5 → 3.5-lite when a model is overloaded or out of quota.
- **Planned additions:** a spelling and grammar check (e.g. Vale or LanguageTool), an HTML validator, and a small validation agent (Flash-Lite) that flags anything not in the client's request. A human approves before anything goes live.
- **Models:** Gemini Flash for routine edits, a stronger model only when checks fail. Use a paid Gemini key for client work, since the free tier hits "overloaded" and quota errors. A Claude subscription doesn't cover API use by custom agents.

## Client flow (agreed; being built in stages)

One pipeline for new clients and changes:

1. Request: an email, or the Get started form (`start.html`) on Cameron's site: a new website, a change, or a question. Send clients `start.html?path=change&site=<their site URL>` for changes: each starter site publishes `photos.json`, so the form shows their current photos to remove or re-describe beside new ones. **Built.** With `intakeUrl` set, the site's forms (and onboarding photos) go to the intake Worker and `node ops/pull.js` brings them into the queue, with a Web3Forms heads-up email; without it they arrive by Web3Forms email and go in with `ops/intake.js`.
2. `node ops/intake.js <email>` sorts it into the queue (`ops/queue/`, not committed): new enquiry, onboarding answers, or a change request from a known client (matched on the saved `contact.email` in `starter/clients/`). Change requests wait for the client to confirm from their saved address (the email is written to `ops/outbox/` until an email service sends it; `ops/confirm.js` marks it confirmed). Unknown addresses and direct emails failing SPF/DKIM are flagged, never confirmed. **Built.** `node ops/queue.js` lists everything.
3. **Cameron approves** and sets the price (small changes: fixed $20; `--price 0` for free family or testimonial work): `node ops/approve.js <id> --price 20 --site <folder>` (or `--close`).
4. New clients use "A new website" on the Get started form, picking add-ons themselves with the price shown (`?path=new&modules=food` still pre-ticks add-ons). `starter/scripts/onboard.js` turns the emailed answers into the client JSON and site. **Built.** Blank headlines stay `[PLACEHOLDER]` for Cameron or AI copy drafting. A real client's site stays blocked until it has their own Web3Forms key (create one at web3forms.com with the client's email; they forward the key; apply a `form-key` change) and, with the food module, their real menu (a `menu-replace` change).
5. Build: new sites by script; changes by `scripts/apply-changes.js` with a list of changes (**built**: wording swaps, opening hours (picked day by day on the forms), public contact details (phone, map address, Instagram, Facebook), the client's form key, a new look (theme), hero photo (a new upload or a gallery photo), logo, gallery add (a list or a whole folder)/describe/remove/reorder, news posts, full menu replace, menu add/remove/price/sold out, price list replace/add/change/remove/hide/photo/note, booking or quote form choices, notice, section order, review add/remove, question add/remove/replace, shop product add/remove/price/Stripe link/sold out/photo, highlight add/remove, how-it-works step add/remove, past project add/remove (with its photo); see `scripts/changes.js`). Wording anywhere, including Lantern Market's stops and section text, is a `text` change. Photos without a description get a placeholder, so the checks catch them. Anything else comes back as "needs a person", for Cameron or the agent.
6. Checks and a Cloudflare Pages preview. **Cameron checks it first**, then the client sees it. Tweaks go back to step 5 (limit the free rounds).
7. The client pays the Stripe link; payment puts it live. **Planned.**

The GitHub side (issue form, `approved` label, `change-request` workflow opening a pull request) is built into every starter site. Never let a request go straight from the public to live: Cameron approves every job and every preview. `site_agent.py` at the root is the one to edit; new-client copies it into each site.

## Working with Cameron

- Keep replies short. Don't explain after each step; give one short summary at the end, never a wall of text. Cameron is often on a phone (on the bus), so previews go up as private artifacts.
- After a piece of work: commit, push, open a PR and squash-merge it, unless Cameron says otherwise. Work on the session's branch, reset from `origin/main` first (`git checkout -B <branch> origin/main`, then force-push), since merged branches only hold old history.
- Art Angel Florist's site stays on its `claude/remaining-work-3am1ua` branch (not merged to `main`) until the client's real details arrive. It is up to date with the starter; its only failing check is the example price list, as intended.
- Demo sites (`"demo": true`) keep everything example-only: shop Buy buttons stay on the page instead of opening Stripe, and search engines are kept out.
- Not wanted for now: an AI classifier at the front (no Jev); Rust; a second framework.
